# assessment-system-design-case-study

多役割の試験運用ワークフローシステムを、後から読み直した分析です。何をするためのシステムだったか、どう作られていたか、セキュリティモデルがどこで破れるか、そして自分ならどう作り直すかをまとめています。

> **出典について。** 元のアプリケーションは、大学の授業課題として学生チームが開発したものです。大学名と科目は意図的に伏せています。確認に必要でしたら個別にご連絡ください。このリポジトリに入っているのは私個人の分析であり、実装を単独で書いたとは主張しません。**チームのソースコードは一切含んでいません。**複製も、改変も、言い換えもしていません。図・表・コードはすべて私が書いたものです。

技術文書の本体は英語の [README.md](README.md) と [`docs/`](docs/) です。この文書は要点だけをまとめたものですので、根拠と詳細はリンク先をご覧ください。

## 二つの部分

- **分析** — [`docs/`](docs/) です。実装から再構成した課題、作られたとおりのアーキテクチャ、ロールとワークフロー、データモデル、根拠つきの10件のセキュリティ所見、そして再設計が入っています
- **答え** — [`src/assessment_policy/`](src/assessment_policy/) です。ワークフローと認可の中核を動く形で実装し、最大の所見が構造的に起こりえないようにしました。テストは672件あります

## 対象のシステム

ある学部が、年に数百件の試験と課題を作成し、点検し、実施し、採点します。試験・小テスト・レポートはそれぞれ、別々の担当者による承認の連鎖を通ります。このシステムの目的は**職務の分離**です。試験問題を下書きから印刷まで進めるには4人の別々の担当者が必要で、他のすべてはそのための仕組みです。実装は Spring Boot の API と React のシングルページアプリケーションで、インメモリデータベースとトークン認証を使っています。

## 中心にある所見

チームはドメインを正しくモデル化していました。setter・checker・moderator・external examiner はロールではなく、課題ごとの関係としてスキーマに入っています。存在する権限チェックも、呼び出し元と**その課題の** checker を突き合わせています。ここを書いた人は問題を理解しています。

**問題はワークフローのサービスにある二つのメソッドです。**一方は、ユーザーに可能な操作を計算します。ロールと課題への関係の両方を見て、慎重に判断しています。もう一方は状態遷移を実行しますが、**ユーザーを一切受け取りません**。コントローラは認証済みの主体を受け取っていながら、それを渡していません。

つまり、慎重な認可の判断は**画面に何を描くか**を決めているだけで、状態を変更するエンドポイントは「ログイン済みであること」しか要求していません。認証さえ通れば、自分が checker ではない問題を承認することも、試験を印刷に回すこともできます。45個のエンドポイントに、メソッド単位の認可注釈は**1件もありません**。設定ではメソッドセキュリティが有効になっているにもかかわらずです。

10件の所見のうち9件が同じ形をしています。**ある層に存在する制御が、それを強制する層で欠けている**という形です。一覧と根拠は [The ten findings](README.md#the-ten-findings) と[セキュリティレビュー](docs/05-security-review.md)にあります。

**予想が外れたことも書いています。**コミットされた秘密鍵が見つかると思って読み始めましたが、ありませんでした。よかった点も記録しています。パスワードは bcrypt でハッシュ化されたうえシリアライズから除外されていて、署名は共有秘密ではなく非対称方式で、秘密鍵は意図的にバージョン管理の外に置かれていました。

## 再設計

10件は独立した10個のバグではありません。**認可を、各エンドポイントが忘れずに行うもの**として設計したという一つの判断と、その9つの帰結です。ですから直し方は、足りないチェックを足すことではありません。足りないチェックを**書きようがなくする**ことです。

**一つの表がすべての正当な遷移と、それを誰が実行してよいかを記述し、システムが答える問いはすべてその表から答えます。**「同じ規則」ではなく、実行時に同じ表を見ます。5つの判断がそれぞれ特定の所見を閉じる形になっていて、対応は [The redesign](README.md#the-redesign) の表にあります。

要になる性質は網羅的に検証しています。あらゆる種別・状態・実行者・操作について、**操作を提示されることと、実行を許されることが同じである**という性質です。監査対象のシステムでは、画面が隠していた操作をAPIが許していた状態のすべてで、このテストが失敗します。[`tests/test_no_drift.py`](tests/test_no_drift.py) と [what I would build instead](docs/06-what-i-would-change.md) をご覧ください。

## この分析の限界

実装は読みましたが、**動かしていません**。起動に必要な署名鍵が、意図的にバージョン管理から外されていてスナップショットに含まれていないためです。したがって2件の所見は、事実ではなく予測として書き、[7番目の文書](docs/07-method-and-limits.md)でもそう明示しています。

再設計はワークフローと認可の中核だけです。Web層もデータベースもフロントエンドもありません。認証・トークンの保管・鍵の管理は、レビューの中で論じてはいますが実装していません。

対象は授業課題で、6人が1学期で作り、ノートPC上のインメモリデータベースに対して動いていました。実際の利用者も実際の試験問題もありません。所見は理解すべきこととして記録したものであって、いくつかは私も犯したはずの誤りですし、実際に犯したものもあります。科目の評価は54/100でした。レビューの内容を読むときの文脈であって、見出しではありません。
